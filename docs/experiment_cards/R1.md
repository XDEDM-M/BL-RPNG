# R1 exploratory card — target LR adaptation

- **Question:** Can better trained multi-boundary HR source models, followed by real target LR Newton-path supervision, improve LR-to-HR rollout accuracy?
- **Historical context:** On development data, target path fine-tuning was 3.73% better than final-only from the path-pretrained source, but labels were nearly collinear with endpoint increments and no endpoint-auxiliary control was run. This is a hypothesis, not a confirmed effect.
- **Source continuation:** warm-start both the existing path-guided and endpoint-only source checkpoints for up to 60 more epochs on the same 128² multi-boundary source HR train/validation data, with Adam, LR 1e-4 cosine decay to 1e-6, early-stop patience 12 after epoch 30. The best source checkpoint is selected by source HR validation. Historical source files remain untouched.
- **Target initialization:** the chosen path-pretrained source candidate is held fixed for every target arm. The primary target comparison changes only final-only versus true accepted-path supervision and the preassigned path-specific parameter.
- **Data:** use the independently generated and integrity-audited Phase-1 development campaign `hrdev_20261012_t20_ss271829`, with `m=4` nested support, 20-step LR validation, and support seed 271829. Initial screening covers four complementary boundary families (tasks 0, 1, 3, 5: high-frequency, amplitude OOD, localized bump, and piecewise smooth); shortlisted configurations then cover all six families. HR development validation is reserved for shortlisted candidates after the LR screen. The older historical LR split has a 10-step horizon while HR validation has 20 steps, so it is superseded for this campaign. The historical HR query is already open and prohibited for tuning.
- **Screen seed:** 42. Deterministic training. Model seeds and support rollouts are held fixed across each pair.
- **Arms:** 9 final-only configurations from the path-pretrained source spanning LR `{1e-4,3e-4,1e-3}` × scheduler/horizon `{cosine-100, multistep-100, cosine-50}`; 9 independently tuned ordinary-transfer configurations on the same grid from the promoted final-only source; 9 lifted LR-scratch configurations on the same grid using full-model adaptation from random initialization; 9 true path-FT configurations spanning LR `{1e-4,3e-4,1e-3}` × target path gradient ratio `{0.05,0.15,0.30}`, 100 epochs, cosine schedule, layer 1, `gamma=2` anneal. The R1 path-FT comparison sets commutator weight to zero so its only added target signal is the accepted path.
- **Selection metric:** mean of four per-task 64² LR-validation 20-step rollout relative-L2 values; report the worst task and each screened family as tail diagnostics. Finalists are compared across all six families. R1 screen does not load HR validation or any query metrics.
- **Budget:** two source-continuation trials, then 36 target configurations × 4 representative task adaptations = 144 initial screen runs, one GPU per process; no distributed training. Dispatch even-index configurations on physical GPU 0 and odd-index configurations on GPU 1 using `--trial-shard 0 2` / `--trial-shard 1 2`. Shortlisted method/configuration winners then run across six families and at least three model seeds. Path-FT uses 9 of 24 main-method trial slots; ordinary transfer and lifted scratch each use 9 of their 12 direct-baseline slots. Stop only for repeated technical failure or the campaign GPU cap.
- **Outputs:** `results/phase1/R1/<trial>/`, compact adapter deltas under `artifacts/checkpoints/phase1/R1/`, all runs in `docs/EXPERIMENTS.csv`.
- **Smoke:** a separate 2-epoch run is implementation-only and excluded from rankings.
- **Promotion:** shortlist source models by source HR validation, then screen target adaptation by aligned target LR validation; validate only short-listed candidates on the independent HR development split. The target runner's initialization, hash, and compacted adapter use the per-trial checkpoint path; full-model LR scratch is independently tunable. The completed initial smoke used the historical frozen path checkpoint and is implementation-only. This screen does not claim HR improvement. R2/R3 get distinct trials and decisions. Confirmation requires a newly frozen boundary manifest and unopened HR query, with the protocol written to `docs/prereg/CONFIRMATORY.md` before query generation.
