# HR-from-scratch m=16 development control

## Question

Can a randomly initialized HR model reach slightly lower 256×256 HR-dev error when it receives a larger target HR support set and enough optimization, and what target-label and GPU costs does that require compared with path-source + LR-NLT adaptation?

## Frozen protocol

- Four representative development tasks: `[0, 1, 3, 5]`; model seed `0`; support seed `271829`.
- Nested support ranks `0..15` from the existing Stage-2 LR support draw are solved at HR256. The first four cases are exactly the earlier m=4 support cases; no new random support seed is introduced.
- Random initialization, full FNO updates, final-only objective, batch size 2, learning rate `3e-4`, cosine schedule, minimum LR `1e-6`, weight decay `1e-4`.
- Train the full 500-epoch cosine schedule, then select the minimum HR-dev checkpoint over the full trajectory. With 16 support rollouts, each epoch contains 4× the transitions of the earlier m=4 run, so the fit performs at least 4× as many optimizer updates. This intentionally gives the HR scratch model HR-dev checkpoint selection.
- Compare against the existing path-source + LR-NLT/comm256 m=4 development checkpoint on the same four tasks. Report that HR scratch receives 4× as many target rollouts; this is a cost/accuracy frontier comparison, not a label-matched algorithm ablation.
- Charge the full 64-rollout target HR label generation, training GPU-hours and checkpoint selection. Report source pretraining as a separate amortizable one-time cost. Keep shared LR-label generation separate and disclose that its existing pool covers six families.
- No confirmation data is generated or read. The confirmation query remains closed.

## Interpretation rule

This experiment tests, but does not assume, the expected outcome that fully trained HR scratch can edge out the path route in accuracy while costing substantially more. Report the measured result even if HR scratch remains worse. This is a one-seed, four-task development comparison and cannot establish a confirmation-level generalization claim.

## Result

- The full 500-epoch schedule completed. Mean best HR-dev error was `0.164269` for HR scratch with m=16, versus `0.056157` for the matched path-source + LR-NLT reference; none of the four scratch tasks reached its path reference.
- Raising scratch support from m=4 to m=16 lowered its mean error by `62.84%`, but m=16 scratch still had `2.925×` the path mean error.
- Training cost was `8.694 GPU-h`, plus `4786.624 s` CPU wall to generate HR support labels. Path target adaptation used `0.487 GPU-h`; its one-time source pretraining used `2.068 GPU-h` and can be amortized.
- This does not support the expected result that fully trained HR scratch slightly outperforms path-source + LR-NLT. It does support a target-side cost advantage for path on these four development families; it is not confirmation evidence.
