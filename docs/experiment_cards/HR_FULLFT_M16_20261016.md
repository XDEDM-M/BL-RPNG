# Source-initialized HR full-FT expert, m=16 (development only)

## Question

How close can a strong source-initialized full-parameter model get to the best path-source/LR-adaptation pipeline when given 16 target HR rollouts per unseen development boundary?

## Why this is the next experiment

The frozen R4 first-accepted-path arm did not improve over either final-only target adaptation or endpoint supervision. Additional path-specific search is therefore stopped. The remaining useful, budget-feasible comparison is the mission's missing HR-target full-FT expert on the same nested m=16 HR support already used by the random-init expert.

## Frozen protocol

- Development tasks `[0,1,3,5]`; model seed `0`; support seed `271829`; nested HR support ranks `0..15`; 16 genuine HR256 rollouts per task; eight independent HR-dev validation rollouts.
- Initialize from the existing multi-boundary path-source checkpoint `artifacts/checkpoints/phase1/R1/source_path_s0_scratch.pt` (SHA-256 `b1e49eb96c558500fd735fba07bd35ee196cd9ee8993846601fda801f5199fbf`). Fine-tune every parameter with final-only supervised loss. This is the source-initialized HR-expert arm; report its source pretraining cost separately.
- Train 250 epochs, batch 2, LR `1e-4`, cosine schedule to `1e-6`, weight decay `1e-4`. The learning rate follows the best measured ordinary full-FT development screen (`1e-4/cos100`) and the schedule is extended for the larger HR support. This is one frozen strong baseline configuration, not an independently searched HR-expert optimum.
- Select the minimum 20-step HR-dev rollout error over all 250 epochs. HR-dev selection is allowed for the oracle expert comparator and does not affect the LR-only path method.
- Compare on exactly the same task, HR support indices, and HR-dev validation indices as the random-init m=16 control. Also report the path-source+LR-NLT m=4 system as a cost/accuracy reference; it uses fewer target labels.
- Query/test data remains closed. No new model seed, support seed, boundary, or support rollout is introduced.

## Budget and interpretation

The four-task cap is 4.7 GPU-h, forecast from the measured 500-epoch m=16 scratch costs scaled to 250 epochs, with the 48 GPU-h reserve untouched. If measured remaining campaign headroom cannot cover the full 4.7 GPU-h cap plus a 0.9 GPU-h buffer after the active scratch queue is terminally charged, do not start. Report all four tasks and observed cost. This 250-epoch expert is budget-limited and is not called saturated; if HR-dev is still improving at epoch 250, report it as right-censored.
