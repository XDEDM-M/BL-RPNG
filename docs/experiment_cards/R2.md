# R2 exploratory card — target multiresolution consistency

- **Question:** Can a label-free 64→128 restriction-commutator loss during LR adaptation reduce the observed LR→HR development gap without target HR labels?
- **Evidence:** R1 path-source final-only at `lr=1e-3` has four-family LR validation `0.02791603` but HR-development validation `0.05602457`. It improves over ordinary transfer by 18.39% on LR validation but only 9.92% on HR development, and loses on piecewise-smooth HR development. True target path supervision is neutral/slightly harmful because its retained labels are nearly endpoint-collinear.
- **Data and selection:** unchanged audited `hrdev_20261012_t20_ss271829`, m=4, support seed 271829, model seed 42, tasks 0/1/3/5. Training and checkpoint selection use only 64² LR support/validation. HR-development evaluation is performed only after LR screening. Query remains prohibited.
- **Method:** same path-source initialization and NLT adapter as the R1 leader; objective `commutator_only`. Compare 64→128 commutator weights 0.01/0.05/0.2 for one prediction step, plus weight 0.05 for two autoregressive consistency steps. Shared final-only R1 arm is the zero-weight control.
- **Budget and stopping:** first run task-0 two-epoch smoke. If finite, run weight 0.05/one-step on four screen tasks; continue neighboring weights only if LR validation is not catastrophically worse and inspect HR development for the shortlisted candidate. One GPU, one process, no distributed work, no `--force`.
- **Smoke acceptance:** finite final and commutator losses/gradients; exact lifted boundary remains enforced; `commutator_loss>0`; checkpoint/result provenance passes read-back; no query path appears in the descriptor.
- **Primary metric:** four-task mean 20-step LR-validation relative L2; HR-development mean and worst family are promotion diagnostics, not within-task checkpoint selectors.
- **Outputs:** `results/phase1/R2/comm_*`, `artifacts/checkpoints/phase1/R2/comm_*`, ledger rows with `round=R2`, and independent HR-development reports for shortlisted candidates.

- The completed weight-0.05 one-step 64-to-128 arm has LR mean 0.02798555 and HR-development mean 0.05430336. All four HR families improve against final-only (0.05602457); this is about 3.07% improvement. Evidence is the four `comm_lr1e-3_cw005_r1_task*_s42_ss271829.json` development reports.
- Next test direct 64-to-256, two-step consistency with weights 0.01/0.05. This targets the actual inference grid while using only interpolated LR inputs and network predictions; it supplies no HR labels. The commutator can be consistently wrong and its refined boundary trace remains coarse-interpolated; independent HR development is required.
- Immutable config: `configs/phase1_r2_direct256.yaml`. Include the ordinary-pretraining competitor with the same weight-0.05 technique, granting the generic training improvement to both methods.
- First smoke weight 0.05/task0, two epochs: finite positive one- and two-step commutator values, finite loss, no path objective, memory below 22 GiB. Then four-task screen at weights 0.05 and 0.01, one GPU at a time. Freeze any shortlist decision before reading query data.

## True LR rollout supervision, before execution

- New module `blrpng/data/rollout_windows.py` filters each 20-step support rollout to its 18 valid three-step starts, preserving the independent rollout as the sampling unit. No horizon crosses a shard; static boundary/condition inputs are explicitly required. Support count remains four independent rollouts, not 72 independent cases.
- `blrpng/training/rollout_supervision.py` recursively advances predicted states for three steps and averages the three endpoint losses with full BPTT. No HR labels are used. Fixed H3 and a horizon curriculum on fixed H3 windows (H1/H2/H3 in successive epoch thirds) are separate candidates; all use LR-validation rollout checkpoint selection. The curriculum uses 18 valid starts throughout, so its first third is not an exact match to the original 20-transition H1 exposure; endpoints also appear in fewer overlapping windows. Report this weighting difference. If curriculum is shortlisted, add its symmetric ordinary-transfer arm before performance conclusions.
- Nine CPU tests cover H1 dataset/loss/gradient equivalence, H3 same-rollout target alignment and collation, unsupported time dependence, full recursive gradients versus a detached negative control, and boundaries at every predicted step.
- Config `configs/phase1_r2_rollout.yaml` includes ordinary transfer and LR scratch with the same general improvement. First fixed-H3 task0 smoke must show supervised_rollout_horizon=3, finite loss/gradients and LR-to-HR inference, before scoring the four-family candidates. Existing R1 one-step results remain the zero-change reference.
