# Stage-2 runtime optimization benchmark: batched CUDA synchronization

- **Question:** Can removing avoidable host/device synchronization and repeated target-boundary lift construction reduce the full frozen confirmation cost while preserving every candidate's LR-validation history and selected checkpoint?
- **Code change:** keep scalar diagnostics on device until epoch aggregation; transfer LR rollout errors once per rollout batch; precompute the 256-grid harmonic lift once for a single-boundary target index and reuse it. Model operations, optimizer, scheduler, support/validation indices, epoch count, and checkpoint rule remain unchanged.
- **Frozen experiment inputs:** `configs/phase1_stage2_pilot.yaml`; `m=4`; model seed `0`; support seed `271829`; task `0` (`high_frequency`); candidates `pilot_pathsource_comm256`, `pilot_ordinary_full_comm256`, and `pilot_lifted_scratch_lr3e-4_cos500_wd1e-4`. Existing pre-change reports/checkpoints are the controls. No HR query or new seed is involved.
- **First-stage budget:** at most 0.6 GPU-h for three task-0 reruns; stop if LR validation selection diverges from the saved baseline beyond exact float32 replay (compare every epoch metric, best epoch, selected checkpoint state hash). Record CUDA-synchronized elapsed time and per-cell GPU-hours. Only if parity holds, benchmark all six development tasks for all three candidates before considering confirmation.
- **Success criterion:** same per-epoch LR-validation values, best epoch, and selected model state; lower measured GPU-hours for every shortlisted arm. Report speedup as matched baseline GPU-hours divided by optimized GPU-hours; do not extrapolate to confirmation until all six tasks and all three arms are measured.
- **Resource accounting:** append every training/evaluation execution to `docs/EXPERIMENTS.csv`; the short prototype failures (vmap/compile) are recorded separately in the research log and budget as engineering GPU use.
